# 写作协议 · 无人值守博客生成

> 本文件是两个定时任务（`github仓库精选` / `AI热点分析`）的**强制执行规范**，不是建议清单。
> 每条"必须/禁止"都配了机械检查方法。协议与 `_drafts/persona.md`、`_drafts/author-log.md`、
> `_drafts/rotation-state.json` 一起构成流水线的全部状态，改这里等于改所有后续文章。

---

## §0 三条总原则（优先级高于一切细则）

**原则一：篇内要不规整，跨篇要一致。**

AI 的特征恰好相反——单篇内部整齐划一（每段等长、每节同构、列表项字数接近），跨篇之间风格漂移（这周像教程，下周像新闻稿）。人类作者反过来：单篇内长短错落、有跑题、有情绪波动；但三个月内所有文章共享同一套口头禅、同一套排版习惯、同一个技术立场。

→ 用 `persona.md`（§1.1）锁定跨篇一致性；用 rotation 状态机（§12）+ 方差检查（§11 C06/C07/C10）锁定篇内不规整。

**原则二：每个形容词都要能被一个数字或一个文件路径替换。**

替换得了就替换，替换不了就删。

- ❌「性能优异」→ ✅「冷启动 0.93s，我测的三次分别 0.91/0.93/1.02」
- ❌「文档完善」→ ✅ 给出 `docs/` 下真实文件清单，或者这句话不存在
- ❌「API 设计非常克制」→ ✅「核心就一个 `execute` 方法，`src/index.ts` 导出表里只有 3 个符号」

**原则三：宁可不发，也不写无法核实的话。**

诚实的空白（「我没测出来」「这块我没读懂」）在读者眼里比流畅的编造更像人。一篇被识破为 AI 的文章，损害大于十篇没发的文章。3 轮自检仍不过 → 放弃本期，登记 abort 原因，不产出文件。

## §1 前置依赖：每次运行必读的 4 个文件

cron agent 每次运行都是失忆的。跨篇一致性只能靠外置状态实现——**没有这一步，第 3 期和第 12 期的文风必然漂移，而漂移正是"这一系列是机器批量生产"最明显的证据。**

若下列文件不存在，本轮 **abort 并报错**，不得凭空生成。

### §1.1 `_drafts/persona.md` — 作者人设（只读，禁止修改）

每次运行都要重新读一遍，不得靠上下文记忆。包含署名、身份口径、主力栈、立场、口头禅池、排版习惯、情绪基线、禁止自称。

### §1.2 `_drafts/author-log.md` — 连续性日志（追加式，永不修改历史行）

每篇发布后追加一段，格式固定：

```
## 2026-03-04 | github-trending-w10 | Page Agent
- 变体: A2 同题擂台 | 标题模板: T3 | emoji 预算: sparse | H2 数: 6 | 字数: 2612
- 我的结论: 会放进下个项目，不动线上。理由：还在 0.x，CHANGELOG 有 3 次 breaking。
- 提到的仓库: alibaba/page-agent (26412 star @2026-03-04T21:07+08)
- 承诺: [ ] 下期测它的 streaming 分支能不能跑通 React 19
- 悬置疑问: DOM 序列化那步对 Shadow DOM 怎么处理，没读懂
- 用过的 H2 标题: 一行代码到底做了什么 / 我 clone 下来跑了 / 跟 TanStack Query 比 / ...
```

**使用规则：**

- 每次运行先读最近 5 条。
- **≥1/3 的运行必须在正文回扣历史**（「上期我说要测 X 的 streaming，测了，翻车了」）。回扣内容必须与 log **逐字对应**，不得美化。
- **承诺队列必须处理**：上次登记的承诺这次要么兑现（写进正文并给出实测结果），要么**明确撤回并给理由**（「上期说要测 streaming，没测，因为它 0.9.3 又把 API 改了，等稳定再说」）。**禁止静默忽略。**
- 悬置疑问同理：有机会就回答，回答了要点明「上期我没读懂的那个问题，这周搞明白了」。

> **这是整套协议里最强的单一反 AI 信号。** 人类博主有连续的人生：上周说的话这周会被自己打脸，承诺会兑现也会赖账，疑问会悬着然后突然解开。AI 系列文章永远是"每期从零开始的平行宇宙"。而这个机制里的连续性是**真实的**——log 是真文件，承诺是真登记，撤回是真撤回，不违反任何诚实条款。

### §1.3 `_drafts/evidence/{slug}.md` — 本篇证据清单（每次运行新建）

格式见 §4.4。所有 T1 级事实必须在此登记。**该目录已 gitignore，绝不提交**——它会暴露所有抓取时间戳和命令，是最直接的机器生产证据。

### §1.4 `_drafts/rotation-state.json` — 配额账本

本次 seed 与所有轮换参数的唯一来源。字段见 §12。

### §2.4 翻译腔专项（中文最隐蔽的 AI tell）

AI 写中文时会在句法层面保留英文结构：

| 症状 | AI 版 | 人写版 |
|---|---|---|
| 名词化动词 | 对该项目的配置进行了优化 | 我把配置改了两处 |
| 「实现了对…的支持」 | 实现了对 TypeScript 的支持 | 能写 ts 了 |
| 系动词回避 | 它作为一个中间层而存在 | 它就是中间层 |
| 被动滥用 | 被广泛采用 / 被认为 | 用的人很多 / 我觉得 |
| 量词冗余 | 一个非常关键的问题 | 关键问题 |
| 「的」字三连 | 我的项目的核心的配置 | 我项目的核心配置 |
| 状语前置 | 在大多数情况下，它会… | 它一般… |
| 长定语前置 | 一个由社区维护的、基于 Rust 的、跨平台的构建工具 | 构建工具，Rust 写的，社区维护，三个平台都能跑 |
| 英文式列举 | A、B 和 C | A、B、C |
| 存在句 | 有一个问题需要被解决 | 有个问题得处理 |

**机械检查正则（命中数必须为 0）：**

```
对.{1,12}进行了
实现了.{0,10}的支持
作为.{1,10}(而存在|的角色)
被(广泛|普遍|认为|采用)
在.{1,10}(方面|情况下|场景中)
对于.{1,12}而言
```

### §2.5 重叠区配额管理（作者真实风格 vs AI tell）

**关键判断**：这位作者的真实文章里就有 🚨、「王炸」、「」、内联 `<style>`、`.highlight-box`、`💡` 洞察框、emoji 前缀 H2。**这些既是他的风格，也是 AI 的高频 tell。不能一刀切禁止**——全禁了反而丢掉博客辨识度，读者会觉得"换了个人写"。

正确做法是**限量 + 不均匀分布 + 跨篇轮换**：

| 重叠元素 | 管理规则 |
|---|---|
| 🚨 / 王炸 / 炸裂 类标题党 | 标题可用（属 persona）；正文禁用"王炸/炸裂"；🚨 每篇 ≤1 且只在标题 |
| 「」概念引号 | ≤2 处/篇；不得包装空洞概念（「规范革命」可以，「极致体验」不行） |
| emoji 前缀 H2 | 预算由 rotation 决定（none / single / sparse 30% / full）；集合与最近 3 篇不同；顺序打乱；**full 模式下也必须留 1-2 个 H2 不带 emoji**（不均匀才是人） |
| 内联 `<style>` 块 | 出现概率 ≤35%；用了必须保证 `jekyll build` 无 warning；class 名与配色必须与最近 3 篇不同 |
| `.highlight-box` / `💡` 洞察框 | 概率 ≤40%；每篇 ≤2 个；内容必须是具体事实或反直觉发现，**禁止是「值得注意的是 + 复述上文」** |
| `📎 参考来源` div | 有真实来源时才写；来源数 ≤5 且全部 fetch 过；**没有就不写这一节**（空节是致命 tell） |
| 感叹号 | ≤5/篇（作者真文章感叹号偏多，设 0 会失真） |

### §2.6 既有文章是反面教材（重要）

本博客 2026 年的既有文章（尤其 `_posts/2026-07-12-alibaba-page-agent.md`、`_posts/2026-07-12-facebook-astryx.md`、`_posts/2026-07-12-impeccable-ai-design.md`）**AI 味很重，不得作为模仿对象**。它们的典型问题：

| 既有文章原文 | 违反条款 |
|---|---|
| H2 序列：`痛点：…` / `核心思路：…` / `实际用起来有多简单？` / `和同类方案的正面对比` / `实际场景思考：它能做什么？` / `目前的局限性` / `总结与展望` | S03（H2 用维度名）、S18（五维度=五个同名 H2）、S02（同构） |
| 「我们内部有个 CRM 系统，表单字段多达 30 多个，新人上手至少要学半天。接入 Page Agent 后…」 | **T3 虚构**（§4.2）——编造了不存在的公司系统与使用时长 |
| 「展望未来，随着大语言模型推理能力的持续提升和 function calling 机制的成熟，我相信"自然语言操控 UI"会从尝鲜功能变成标配能力…而 Page Agent，就是推动这个转变的先行者之一。」 | §9.2 三条禁令全中；可移植性测试 FAIL（换成任何项目都成立）；时间无关性测试 FAIL |
| 「当然，Page Agent 也有它的边界。首先…其次…最后…不过这些问题都在快速迭代中。项目团队在 GitHub 上非常活跃，issue 响应速度很快。」 | §2.1-L 万金油批评 + S11 对称列表 + 无任何可核对事实 |
| 「API 设计非常克制」「定位非常清晰」「效果超出预期」「这是非常有社会价值的应用场景」 | §2.1-B 空洞强调词，全部无支撑 |
| 3 列对比表，7 行，每格 2-6 字，工整对称 | S07（应为 ≥4 列或畸形表） |
| 每节之间都有 `---` | §2.2 分隔线配额 |

**可以继承的只有**：技术判断的方向感、敢下结论、`项目地址：` 结尾、中文描述性 alt 文本、7 键 frontmatter 格式。
**必须抛弃的**：上述全部结构与措辞。

> 唯一接近合格的是 `_posts/2026-06-15-webmcp-vs-puppeteer.md` 的 H2 命名——
> `痛苦回忆录` / `破局者` / `尝鲜指南` / `扒开源码` / `降维打击对比` / `写在最后`。
> 这些标题**不可移植**（拿到另一篇文章就不合适），符合 §7.0 的检验法。这是正确方向的样本。

## §3 人味信号 H01-H14（可确定性执行）

agent 没有人生，但它**有 shell、有网络、有仓库、有自己在这个博客上的历史**。以下每项都能机械执行。

**H01 · 奇数精度数字**
每篇 ≥8 个可核对数字，其中 ≥3 个必须是"丑精度"：带小数（1.73s）、四位数（26,412）、精确到个位（280 行）、非整百分比（63.4%）、带毫秒的时间戳。**禁止全部四舍五入到好看的整数。**
AI 写「约 2.6 万 Star」，人写「26,412，我今天 21:07 抓的」。

**H02 · 中途改主意**
每篇 ≥1 处「我一开始以为 X，跑完发现 Y」。**前置条件：Y 必须是本轮真实观察**（evidence manifest 有对应命令与输出）。
制造方法：真的去跑边界情况——空输入、超长输入、断网、错误 API key、node 版本不匹配——真实惊喜自然会来。
若跑完确实没有意外，写「我原本预期它会在 X 上翻车，跑了 40 分钟没翻出来，可能是我场景太简单」。**这也是合法的人味。**

**H03 · 未经润色的原始输出**
≥1 个代码块是**直接粘贴**的真实 CLI 输出 / 报错 / warning / 测试结果，保留丑陋部分：deprecation notice、peer dependency 警告、非零退出码、对齐错乱的表格、`npm WARN`。
AI 会贴干净的 happy path，人会贴一屏红。

**H04 · 带编号的真实引用**
≥2 个 issue / PR / release / commit / discussion 引用，**全部必须实际 fetch 验证存在**，且文中描述与抓到的标题/正文一致。
写法要带具体细节：「`#4127` 有人在 Windows 上复现了路径分隔符问题，维护者 3 月 1 日标了 wontfix，理由是不打算支持 Windows」。**禁止凭印象写编号。**

**H05 · 与 persona 现有栈正面比**
每篇 ≥1 次把作者正在用的东西拉进来，并明确表态"我现在用的是 X"、"我为什么还没换"。persona 主力栈见 `_drafts/persona.md`。

**H06 · 显式承认不知道**
每篇 ≥2 处能力/经验边界声明，且必须是真的没做（manifest 里查不到对应条目）：

- 「Shadow DOM 那段我没读懂，跳过去了」
- 「只跑了三次，样本不够下结论」
- 「可能是我 node 22 的环境问题，换 20 的人可以试试」
- 「这块我不熟，说错了欢迎指出来」

> AI 被训练成什么都要答。**主动留下空白是最强的反 AI 信号之一。**

**H07 · 句长与段长方差（硬指标）**

- 存在 ≥2 个 ≤6 字的短句（「能跑。」「没了。」「这点我不认同。」）
- 存在 ≥1 个 ≥50 字的长流水句（逗号串联、口语化、可以语法上不完美）
- 段落字数：最大/最小 ≥4，标准差 ≥40
- 必须有 1 段 ≤2 行，也必须有 1 段 ≥8 行

**H08 · 带理由的真批评**
≥1 处负面判断，理由必须是可核对的技术事实。**禁止使用 §2.1-L 万金油批评。** 合格样例：

- 「`docs/api.md` 停在 v0.4，v0.9 新增的 3 个选项一个没写」（可核对：文件 mtime + 内容 diff）
- 「它把 API key 明文写进生成的 HTML 里，`src/gen.ts:142`，这在生产上是事故」（可核对：行号）
- 「README 说 10x faster，我测的是 2.6x，同一台机器同一个数据集」（可核对：命令）

**H09 · 非对称列表**
若出现优点/缺点类列表：**条数必须不相等**（如 4 优 2 缺、2 优 5 缺），**且项长标准差 ≥8 字**（有的项一行，有的项四行带例子）。严格对称的 3+3 是 AI 签名。
更好的做法：其中一边干脆不用列表，用一段带情绪的叙述。

**H10 · 口头禅配额**
从 persona 池取 2-4 个，**不得更多**（过度使用同样可疑，会变成新模板）。每次运行取的组合与最近 3 篇不同。

**H11 · 一处合法跑题**
每篇允许并鼓励 1 段与主线只有松散关联的真实内容：某个库的版本史八卦、某个 API 为什么被废弃、某年某个框架的旧事。**必须真实可核对。**
人类的注意力会漂，AI 的主题一致性太高。篇幅 ≤150 字，且不得出现在开头和结尾。

**H12 · 时间锚**
明确写出抓取时间、版本号、「截至本文发布」、「我今天下午」（**仅当运行确实在下午**——用系统时间判断，不得编造）。
人类博客有强烈的时间感，AI 文章悬浮在时间之外。

**H13 · 拒绝面面俱到**
每篇 ≥1 处显式取舍声明：「这篇不讲部署，我不关心」「SSR 那部分我跳过了，我用不到」「benchmark 我就不贴了，别人的机器不是我的机器」。
**AI 求全，人有偏好。**

**H14 · 排版不完美（受控）**

- 不是每件事都列点：至少一处用自然段把三件事讲完
- 列表项结尾标点允许不一致（有的带句号有的不带）
- 允许一处括号里的自言自语（「（别问我为什么知道）」——**仅当为真**）
- 代码块语言标注允许偶尔省略（人类偷懒），但**不得标错**

## §4 诚实政策

### §4.1 三层断言分级

| 层级 | 定义 | 允许的第一人称表述 | 前置条件 |
|---|---|---|---|
| **T1 实测** | 本轮运行中 agent **真实执行**的命令、**真实读取**的文件、**真实抓取**的 URL/API | 「我跑了」「我 clone 下来」「我读了 `src/x.ts`」「我抓到 Star 是 26,412」「我装了 v0.9.2」 | 必须写入 evidence manifest：命令原文 + 输出片段 + UTC 时间戳 |
| **T2 判断** | 观点、偏好、预测、审美、取舍、意图 | 「我觉得这设计很蠢」「我下个项目会用它」「我猜半年内会火」「我不推荐 Windows 用户」 | 无需前置条件（观点不可证伪即不构成造假），**但必须紧跟一个 T1 事实作为理由** |
| **T3 虚构** | 未发生过的经历、他人、对话、场景、情绪记忆、时长 | **全部禁止** | — |

**升级规则**：任何想写成 T1 的句子，若 manifest 里查不到对应条目 → 降级为 T2（改成「我觉得/我猜/我大概会」）或直接删除。**不允许"感觉像真的所以写上"。**

### §4.2 T3 禁止清单（具体到句型）

- **虚构职业/组织**：「我在某大厂」「我们团队」「我司」「我们线上」「我同事」「我老板」「我朋友小王」「读者私信问我」「评论区有人提到」（除非真去抓了本博客该文的 Waline 评论）、「我们内部有个 CRM 系统」
- **虚构场景**：「昨天我在地铁上想到」「上周开会的时候」「深夜改 bug 时」「面试的时候被问到」
- **虚构时长**：「我用了三个月」「我们生产环境跑了半年」「我关注它两年了」「新人上手至少要学半天」——cron 首轮不可能有历史时长。**唯一合法时长来源是 `author-log.md` 的真实日期跨度**（「我上个月在这个博客里写过它」——这是真的）
- **虚构对话与引语**：任何引号内的话必须来自抓取原文（H04 / §5.6）
- **虚构失败细节**：「我一开始装错了 node 版本」——除非本轮真的装错了
- **虚构情绪记忆**：「那一刻我激动得睡不着」「看到结果我愣住了」「效果超出预期」
- **虚构第三方数据**：DAU、营收、市占率、团队人数、下载量（除非 API/一手文件实抓）
- **虚构身份权威**：「作为三年 React 使用者」——除非 persona 明确授权该口径

### §4.3 T3 冲动的合法替代路径

| 想写（T3） | 改写成 |
|---|---|
| 我在生产环境用了半年 | 我在本地跑了 40 分钟，够判断它能不能起来，不够判断它稳不稳 |
| 我们团队都觉得好用 | 我一个人觉得好用，团队规模的事我没经验 |
| 上周我在 GitHub Trending 看到它 | **这句合法**——cron 确实从 trending 抓的。写「今天（3 月 4 日）GitHub Trending 前端榜第 3 位，21:07 抓的」 |
| 我用了三个月才发现这个坑 | 我照 README 走第二遍的时候踩到这个坑（前提：真踩到） |
| 这让我很兴奋 | 这个 API 设计我觉得比 X 那边干净，理由是……（转成 T2 + T1 理由） |
| 我朋友的公司靠它省了一半人力 | 删 |
| 我之前一直在找这样的工具 | 我上个月在这个博客里抱怨过 X 不好用（前提：author-log 真有这条） |
| 我们内部有个 30 字段的 CRM 表单 | 我拿本博客的评论表单试了，6 个字段，能填对 5 个，日期那个填成了时间戳 |

### §4.4 evidence manifest 格式

`_drafts/evidence/{slug}.md`，每条 T1 事实一行：

```
N-01 | star 数 26412 | GET api.github.com/repos/alibaba/page-agent | 2026-03-04T13:07:22Z | resp.stargazers_count
N-02 | 冷启动 0.93s | `time npx page-agent run demo/` ×3 | 2026-03-04T13:41:05Z | 0.91/0.93/1.02
C-01 | prompt 硬编码在 88 行 | clone @ a3f9c21, src/prompts.ts | 2026-03-04T13:22Z | sed -n '85,92p' 原文
I-01 | #4127 Windows 路径 bug, wontfix | GET .../issues/4127 | 2026-03-04T13:50Z | title + labels 原文
U-01 | https://... | HTTP 200 | 2026-03-04T13:52Z | 抓到的关键句
```

前缀含义：`N-` 数字类、`C-` 代码/文件类、`I-` issue/PR/release 类、`U-` URL 类、`R-` 实跑输出类。

**正文中每一个数字、每一段引用代码、每一个编号、每一个 URL，都必须能在这份 manifest 里找到对应行。** 自检 C04/C18/C20/C21 就是拿正文反查 manifest。

## §5 事实安全规则（针对 live web 研究）

### §5.1 核心律令

> **数字无来源即不写数字。**

降级阶梯（只能逐级降，禁止跳级编造）：

1. 精确值 + 抓取时间 + 来源（首选）：`26,412（2026-03-04 21:07 UTC+8 抓的）`
2. 约数 + 来源：`2.6 万左右，GitHub API 今天返回的`
3. 量级：`Star 五位数`（**仍需来源，只是不写具体值**）
4. 删掉这句话

### §5.2 抓取优先级与采信规则

一手 > 二手，**只有一手可写成事实**：

1. 官方 API（GitHub REST/GraphQL、npm registry、PyPI、crates.io）
2. 仓库内真实文件（clone 后实读，记录 commit SHA）
3. 官方 blog / CHANGELOG / release note / 官方文档 / status page
4. 当事人本人的账号原文（可抓取、可链接）
5. 主流媒体一手报道 → **必须标注「据 X 报道，我没找到一手来源」**
6. 转述、聚合站、论坛二手复述 → **不得作为事实写入**

### §5.3 分类目规则

| 类目 | 规则 |
|---|---|
| **Star / Fork / Watch** | 必须来自 GitHub API 实抓，正文必须带抓取时间或写「截至本文发布」。禁止把四舍五入值当精确值。**增长类断言（「一周涨 2 万」）必须有 `rotation-state.json` 的上期快照或第三方 star-history 数据，否则只能写当前值不能写增速** |
| **下载量** | npm `downloads` API / PyPI stats，带时间窗口（「上周 3.2 万」必须写明是哪一周） |
| **版本号** | `npm view <pkg> version` / releases API / 实读 `package.json`。禁止写「最新版本」而不给号。**禁止凭记忆写版本** |
| **API 签名 / 配置项** | 必须实读源码或实跑，记录文件路径 + commit SHA。**禁止凭训练记忆写** |
| **代码片段** | 只能来自实读的仓库文件（附路径 + SHA）或自己执行的命令。禁止「重构/美化」官方示例后仍称其为官方示例 |
| **融资金额 / 估值 / 营收 / 裁员人数** | **默认禁止**。仅当有官方公告、SEC/监管文件、公司 blog 时可写；媒体转述必须双源且标注「未经证实」 |
| **benchmark / 性能数字** | 只写自己实测的（附命令、机器、次数、原始数据）。引用他人 benchmark 必须给原文链接并写明测试环境 |
| **时间表述** | 所有「最近/上周/刚刚/日前/近日」必须换成绝对日期 |
| **引语** | 逐字 + 链接 + 抓取时间。英文引语保留原文，译文另起一行并标「我的翻译」。**禁止转述后加引号** |
| **URL** | 全部必须实际 fetch 成功（2xx/3xx 且内容与文中描述一致）。**禁止按规律拼 URL**（尤其 issue 编号、博客 slug、docs 路径）。写不出编号就不写编号 |
| **图片** | 不引外部图片，全部本地生成（见 §13）。禁止 base64 内联 |

### §5.4 禁止推算冒充事实

不得由 Star 数推「用户数」；不得由 commit 频率推「团队规模」（除非实读 CONTRIBUTORS/CODEOWNERS）；不得由 npm 下载量推「公司采用率」；不得由 issue 数量推「质量差」。
所有推论必须显式标为推论（「我猜」「看着像」）。

### §5.5 官方宣传语处理（同时是人味信号）

README 里的营销话**不得直接转述为事实**，必须以「声称」形式呈现，并尽量配上自己的实测反差：

- ❌「它比 X 快 10 倍」
- ✅「README 第一行写着 10x faster。我在同一台 M2、同一个数据集上测，是 2.6x。差得有点多，可能是我的用例不对，issue #892 里有人测出来 8x。」

**质疑官方宣传是博客作者最典型的行为，AI 倾向于照抄 README。**

### §5.6 争议事件规则（Job B 专用）

- 必须呈现 ≥2 方原始说法，逐字引用 + 链接
- 两方冲突时，**冲突要写进正文**（「A 的声明说 X，B 的回应说 Y，这两句话对不上」）——这既诚实又是极强人味
- 禁止法律/道德定性词：违法、欺诈、造假、恶意、抄袭——除非有判决书、监管处罚文件或当事人书面承认
- 禁止人身评价
- **允许并鼓励结论为「我不知道谁在说真话」**

### §5.7 找不到材料时的处置

某必需要素（如「当前局限性」）经充分调研仍无可核实材料时：

- **禁止**编造局限性
- **禁止**使用 §2.1-L 万金油批评
- **必须**写诚实空白：「我跑了 40 分钟没碰到明显问题。这个时长不够看出稳定性问题，等我用久了再补一篇。」
- 并在 `author-log.md` 登记为悬置疑问，下期回补

### §5.8 数据源预算与限流（实测值，勿凭记忆）

无 token 时的真实配额，2026-09-09 实测：

| 数据源 | 配额 | 实测依据 |
|---|---|---|
| GitHub **Search** API | **10 次/小时** | `x-ratelimit-limit: 10`、`x-ratelimit-resource: search` |
| GitHub **core** REST（repo/issue/PR/release） | 60 次/小时 | 官方文档，与 Search 分开计 |
| GitHub Trending **HTML 页面** | 无 API 配额 | `https://github.com/trending?since=weekly` 返回 HTTP 200 |
| npm downloads API | 宽松 | `api.npmjs.org/downloads/point/last-week/react` 正常返回 |

**⚠️ Search 的 10 次/小时是最容易踩的坑。** 一次运行如果按语言/topic 分别查 6 次，
就用掉了 60% 的额度；再加上重试或临时补查，会在运行中途 403，
而那时候证据清单已经写了一半——正文数字无法反查，只能整篇 abort。

**规则：**

1. **优先级：无配额的 HTML 源 > core REST > Search API。**
   Trending 页面能拿到周榜和「本周新增 star」，这恰好是 Search API 给不了的字段，
   而且不花配额。先用它定候选，再用 Search API 补「本周新建」这一类它独有的查询。
2. **Search API 一次运行最多 3 次查询**，把条件合并（用 `topic:ai topic:llm` 组合、
   `language:` 取舍），不要为每个维度各发一次。
3. **每次调用前读 `x-ratelimit-remaining`**。为 0 就不要再发，直接走降级路径。
4. **降级路径（不是 abort）**：Search 额度耗尽 → 只用 Trending HTML + core REST 完成选题与核实。
   这两个源的额度足够支撑一篇合格文章。只有当**一手来源整体不可用**
   （Trending 也抓不到、core REST 也 403）时才按 §11.2 登记 abort。
5. 收到 403/429 时**读 `retry-after` 与 `x-ratelimit-reset`**，不要在循环里重试——
   重试只会把额度耗得更干净。把响应体登记进证据清单，然后走降级。
6. **禁止**因为额度不够就改用记忆里的 star 数或版本号（§5.3）。宁可少写一个数字。

## §6 结构性反模式禁止清单

| ID | 禁止 | 机械检查 |
|---|---|---|
| S01 | H2 数量固定在 5-7 | H2 数 ∈ {4,5,6,7,8,9}，由 seed 决定，且 ≠ 上一篇 |
| S02 | 所有 H2 同一语法形式 | H2 首字必须覆盖 ≥3 种类型（动词/名词/数字/代词/问句/感叹/英文词）；禁止全部动宾结构；禁止全部问句 |
| S03 | H2 标题使用维度名 | 禁止 H2 是纯维度词：`功能`/`特性`/`优势`/`优点`/`缺点`/`局限`/`局限性`/`使用场景`/`应用场景`/`未来展望`/`展望`/`总结`/`小结`/`背景`/`实践`/`评价`/`对比分析`/`痛点`/`核心思路`/`起因`/`经过`/`影响`/`事件背景`/`事件回顾`/`深远影响`。H2 必须由本篇具体内容生成（见 §7.0） |

| S05 | 每节段数相同 | 各节段数的极差 ≥2 |
| S06 | 每篇必有表格 | tableMode ∈ {none, wide(≥5列), irregular, prose}，由 seed 决定；`none` 权重 ≥30% |
| S07 | 3 列对比表 | 若出表格，列数 ≥4 或为「畸形表」（含 N/A、含「我没测」列、某行只有半格内容、表头不是「特性/A/B」而是具体维度名、单元格字数差异大） |
| S08 | 「总结」节复述开头 | 结尾节与前 200 字的 3-gram 重合率 <15%；且结尾节禁止出现开头节用过的句子骨架 |
| S09 | 固定开头 | 禁止：自我介绍、「在阅读本文前」、定义句（「X 是一个…的…」）、时代背景句、无数字的「最近 X 很火」。开头 60 字内必须出现：代码/命令、报错原文、精确数字、issue 或 commit 标题原文、不加修饰的断言——**五选一** |
| S10 | 段落长度趋同 | 段落字数标准差 ≥40，且 max/min ≥4 |
| S11 | 列表项等长 | 同一列表内项字数标准差 ≥8；且至少一个列表的项数不是 3 的倍数、不是偶数对称 |
| S12 | 自问自答过多 | 「那么，…？」「你可能会问」「这意味着什么？」合计 ≤1 |
| S13 | 参考来源造假 | 无真实来源则**整节不写**；禁止写「参考资料：官方文档」这种无链接条目 |
| S14 | 同句式模板重复 | 任一 4-gram 在全文出现 ≥3 次即 FAIL（`的`/`了`/`是` 等虚词 n-gram 白名单除外） |
| S15 | 跨篇 H2 撞车 | 本篇任一 H2 与最近 5 篇的 H2 字符串完全相同 → FAIL；4-gram 重合 ≥2 → FAIL |
| S16 | 每篇都用 `<style>` | 概率 ≤35%；class 名/配色与最近 3 篇不同 |
| S17 | 加粗滥用 | `**…**` ≤6 处，禁止包裹形容词 |
| S18 | 必需维度 = 同名 H2 | 见 §7.0 |
| S19 | 全文无第一人称具体动作 | 「我 + 实测动词」≥3 处，且每处对应 manifest 条目 |
| S20 | 篇幅趋同 | 目标字数由 seed 决定 ∈ {1800,2200,2600,3000}±200，且与上一篇差 ≥300 字 |
| S21 | 跨篇正文查重 | 与最近 5 篇做 5-gram 重合率 <8%（防 cron 每期产出同一篇） |
| S22 | 每节都以转折词开头 | 「而/但/因此/所以/不过」段首合计 ≤3 |
| S23 | 每个代码块都是 happy path | ≥1 个代码块含 warning / deprecation / 非零退出码 / 丑格式（H03） |
| S24 | front matter 缺失或错格 | 必须 7 键齐备且顺序固定；`date` 与文件名日期一致；slug 与文件名一致；tags 全部单 token；tags 优先取自博客既有集合 |

## §7 Job A 骨架：GitHub Trending（AI + 前端，周更）

### §7.0 覆盖规则（最重要的一条）

五个必需维度——**功能 / 与同类产品对比的优势 / 使用场景 / 当前局限性 / 未来展望**——是**必须覆盖的内容**，不是**必须存在的章节**。

硬性规定：

1. **禁止**五个维度对应五个 H2。
2. **禁止**任何 H2 标题是维度名（S03）。
3. 五个维度中，**最多 2 个**可以拥有独立 H2，其余必须**嵌入**其他章节、以表格列形式、以列表项形式、或以单段形式出现。
4. 每个维度的**落点和形式**由所选变体决定，且相邻两期不得采用相同的落点组合。
5. H2 标题必须由本篇具体内容生成。**检验法：把这个 H2 拿到另一篇同类文章里，如果不合适，说明它是合格的。**

| ❌ 不合格 | ✅ 合格 |
|---|---|
| `## 局限性` | `## Windows 上我没能跑通` |
| `## 使用场景` | `## 我会在哪儿用它，以及不会在哪儿用` |
| `## 未来展望` | `## 如果 0.10 把 streaming 加上` |
| `## 功能特性` | `## 一行代码到底做了什么` |
| `## 横向对比` | `## 跟 TanStack Query 比，它少了什么` |
| `## 目前的局限性` | `## 跨域 iframe 那步直接报错了` |

### §7.1 变体 A1 · 单主角深挖

**选 repo 规则**：从本周 trending 里选 1 个，优先级：能 clone 并跑通 > 有可读源码 > 非 awesome-list / 非纯文档站。若首选跑不通，改用 A4。

```
开头（60 字内出现代码/数字/报错之一）
H2 ×1  它到底做了什么          → 功能（贴着代码讲，不列 feature list）
H2 ×2  我 clone 下来跑了        → 功能 + 局限（实跑，含丑输出 H03）
H2 ×3  跟 <persona 现有工具> 比  → 优势（必须点名 persona 栈里的具体库）
H2 ×4  我会在哪儿用它           → 场景（正反面都写：会用 + 不会用）
H2 ×5  <具体失败点>            → 局限（真实报错 / 真实 issue 编号）
        └ 末尾嵌 ≤150 字展望     → 展望（不独立成节，见 §9）
H2 ×6  顺手记一笔              → 本周其他 trending 3-5 条，每条 ≤40 字，
                                 格式故意不统一（有的带链接有的不带，
                                 有的只有半句判断）
结尾：一个具体决定（非总结）
```

**参数**：emoji 预算 none 或 sparse｜表格 none｜字数 2600±200｜结尾类型 decision

### §7.2 变体 A2 · 同题擂台

**选 repo 规则**：从 trending 找 2-4 个功能重叠的项目。

```
开头：我的一个具体问题（不是"最近 X 很火"）
H2 ×1  我测了什么，没测什么     → 评测口径（显式声明边界，H13）
H2 ×2  <repo A 名>            → 长度最长
H2 ×3  <repo B 名>            → 长度中等
H2 ×4  <repo C 名>            → 长度最短（三节字数必须明显不等）
H2 ×5  <畸形对比表>           → ≥5 列，必含"我没测"列或 N/A
H2 ×6  我会选哪个，为什么另两个不选 → 优势 + 局限合并
结尾：一行判决（one-line-verdict）
```

**维度映射**：功能 = 各 repo 节首句｜优势 = 对比表 + 「为什么不选」｜场景 = 评测口径节里说明我的使用场景｜局限 = 每个 repo 节内 ≥1 条｜展望 = 写成「什么条件下我会换」（有条件预测，见 §9 判据 2）

**参数**：emoji sparse｜表格 wide/irregular｜字数 3000±200｜结尾 one-line-verdict

### §7.3 变体 A3 · 主线 + 碎片周记

```
开头：碎片中的一条直接开场（不预告全文结构）
H2 ×1-3  主线 repo（占 60%），三节标题自由，
         五维度全部在这三节内消化，不显式分节
H2 ×4  这周另外几笔（占 40%）
       → 3-5 条，用 H3 或加粗段首，条目长度 1 行到 5 行不等，
         有的带代码，有的只有链接 + 一句吐槽，
         有的写"没细看，标个记号"
结尾：open-question 或 next-week-hook
```

**维度覆盖**：仅对主线 repo 完整覆盖五维度；碎片 repo 只需功能 + 一句判断。
**这是最"人"的结构**——因为它明显不规整。

**参数**：emoji full（打乱、留 1-2 个空）｜表格 none｜字数 2200±200｜结尾 next-week-hook

### §7.4 变体 A4 · 翻车实录

**触发条件**：A1 首选 repo 跑不通时自动切换；或 seed 命中（**每 6-8 周至多 1 次**——每周翻车不可信）。

```
开头：一段真实报错原文（不改写）
H2 ×1  我本来想解决的问题        → 场景
H2 ×2  第一个库：<名>，卡在…    → 期待（功能）+ 真实失败原因
H2 ×3  第二个库：<名>，能跑但…   → 局限
H2 ×4  最后我用了 <名>          → 优势（在对比中显现）
H2 ×5  我给 <repo> 提了个 issue  → 展望（真实动作：可核对的 issue 编号；
                                  若未真提，改写成"我打算提，草稿在这"并真的贴出草稿）
结尾：TODO 清单（3-5 条，未完成状态）
```

**参数**：emoji none｜表格 none｜字数 2200±200｜结尾 todo-list

### §7.5 变体 A5 · 低产周（短帖）

**触发**：每 5-7 周一次，或本周 trending 确实无料（判断标准：前端/AI 类目 star > 500 且非 awesome-list 的项目 < 3 个）。

**结构**：800-1200 字，3-5 条碎片，无表格，无独立展望节，开头直接承认「这周没什么大东西」。五维度只对其中 1 个 repo 覆盖，其余只写功能 + 一句判断。

> **短帖是强人味信号**：AI 内容农场永远稳定输出 3000 字。人类博主有低产周。

**参数**：emoji none｜表格 none｜字数 800-1200｜结尾 one-line-verdict

### §7.6 Job A 轮换算法

```
weekIdx = floor((today - 2026-01-05) / 7)          # 2026-01-05 为周一
cands   = [A1, A2, A3, A4, A5]
pick    = cands[(weekIdx + saltA) % 5]
if pick == lastRun.variant:      pick = cands[(idx+1) % 5]
if pick == A5 and weeksSinceLastA5 < 5: pick = A1
if pick == A4 and weeksSinceLastA4 < 6: pick = A1
if A1/A4 首选 repo clone 失败:    pick = A4
```

其余参数（emoji 预算、表格模式、H2 数、开头类型、结尾类型、目标字数、标题模板）各自独立用 `(weekIdx × 质数 + salt) % len` 派生，并与 `rotation-state.json` 中最近 3-5 条比对去重。完整派生表见 §12。

## §8 Job B 骨架：互联网 / AI 热点事件分析

三个必需维度——**起因 / 经过 / 影响**——同样适用 §7.0 的覆盖规则：**禁止**三个 H2 就叫「起因」「经过」「影响」，也禁止叫「事件背景」「事件回顾」「深远影响」。

### §8.1 变体 B1 · 时间线正叙

```
开头：一个精确时间戳 + 那一刻发生的具体事（原文引用）
H2 ×1  在这之前                → 起因（用具体数字/版本/日期锚定原状态）
H2 ×2  <时间线标题，如"72 小时"> → 经过：逐条带绝对时间 + 时区 + 来源链接
                                 必须包含 ≥1 条"后来被改口/删除的说法"
                                 （能抓到 archive.org 或 edit history 时）
H2 ×3  对用 <具体技术> 的人     → 影响层 1（给可执行动作）
H2 ×4  对 <具体厂商/项目>       → 影响层 2（给可核对指标）
H2 ×5  接下来要盯的三件事        → 展望（每件给一个可核对的观察点，
                                 如"看 X 的 CHANGELOG 有没有出现 Y"）
结尾：open-question
```

**影响节硬性要求**：必须分对象，且**每个对象都要落到一个可执行动作或可核对指标**。禁止「将产生深远影响」。
合格样例：「如果你项目锁在 openai 4.x，先别升 5.x——4.x 的 `response_format` 在 5.x 里换了字段名，我本地跑了一遍，报 `InvalidRequestError`，原文在下面。」

**参数**：emoji none 或 single｜表格 irregular（时间线表可用，但列数 ≥4 且含「来源」列）｜字数 2600±200

### §8.2 变体 B2 · 倒叙：从结果开始

```
开头：最新状态（原文引用 + 精确数字），不做任何铺垫
H2 ×1  现在是什么样              → 结果先行
H2 ×2  往回倒 <N> 天             → 经过（倒序时间线，每条带来源）
H2 ×3  一开始是怎么回事          → 起因
H2 ×4  谁受影响，怎么办          → 影响（合并成单节，用不规整列表）
        └ 末尾嵌 ≤200 字展望
结尾：one-line-verdict
```

**为什么反 AI**：AI 的默认叙事是「背景→发展→高潮→总结」的线性结构。倒叙打破了这个签名。

**参数**：emoji none｜表格 none｜字数 2200±200

### §8.3 变体 B3 · 多方证词对照

```
开头：两句互相矛盾的原话，直接并排贴出，不评论
H2 ×1  官方怎么说的             → 逐字引用 + 链接 + 抓取时间
H2 ×2  当事人/另一方怎么说的     → 同上
H2 ×3  社区怎么说的             → 抓 HN / Reddit / V2EX / X 的具体帖子，
                                给账号 + 链接 + 原文，不用"网友表示"
H2 ×4  这几句话对不上的地方      → 交叉比对（本篇核心价值）
H2 ×5  事情的起点               → 起因（压缩，≤300 字）
H2 ×6  我的立场（或者：我没有立场）→ 影响 + 展望合并
结尾：允许写"我不知道谁在说真话"
```

**这是最不像 AI 的结构**——AI 通常不会做证词交叉比对，也不会承认无法判断。

**参数**：emoji none｜表格 prose（不用表格，用引用块）｜字数 3000±200

### §8.4 变体 B4 · 一个技术切面

```
开头：一段代码 / 一个错误码 / 一行 benchmark 数字
H2 ×1  发生了什么（≤300 字）    → 起因 + 经过高度压缩
H2 ×2-4  技术剖析主体（占 70%）→ 读源码、跑复现、算数字
H2 ×5  这件事对谁有实际影响      → 影响（落到具体人群 + 具体动作）
        └ 末尾嵌展望（≤200 字）
结尾：todo-list 或 decision
```

**适用**：事件本身信息量不足但有技术细节可挖时（一次宕机、一个 benchmark 异常、一个 CVE）。

**参数**：emoji none｜表格 wide（技术数据表）｜字数 2600±200

### §8.5 变体 B5 · 多事拼盘

事件密集时使用：2-3 个事件，每个 600-900 字，**格式故意不统一**（一个用时间线，一个用引用对照，一个只有三段话）。起因/经过/影响在每个事件内覆盖，但呈现形式各异。

**参数**：emoji sparse｜表格 none｜字数 2600±200

### §8.6 Job B 轮换算法

与 Job A 独立：`runIdx = floor((today - 2026-01-01) / 1)`，`pick = cands[(runIdx + saltB) % 5]`，同去重规则。

**额外约束**：

- B3 与 B4 **不得连续使用**（都重度依赖一手抓取，连续使用会因材料不足降质）
- 若当日一手材料抓取失败率 > 30%，**强制降级为 B4 或 abort**

## §9 「未来展望」非空心化专章

> 用户点名要「未来展望」，而自然写作规范把空心展望列为 AI tell。**矛盾的解法不是删掉这一维度，而是把它从「预测」改造成「赌注」**：预测是廉价的（AI 什么都能预测），赌注是有代价、可验证、有具体对象的（只有真在跟进的人才写得出来）。

### §9.1 四条判据（必须满足 ≥2，否则删段重写）

**判据 1 · 具体锚点** — 必须指向一个**可核对的对象**，并在 evidence manifest 里有对应条目：

- 仓库里的 `ROADMAP.md` / `docs/roadmap` 文件路径
- GitHub 上的 open milestone 名称 + 编号
- 已存在的 PR / issue 编号（含维护者的表态原文）
- `CHANGELOG.md` 里写着 `planned` / `deprecated` / `TODO` 的行
- npm `dist-tag` 上的 `next` / `beta` / `canary` 版本号
- 官方 blog 里带日期的路线图声明
- `package.json` 里的 `engines` / `peerDependencies` 变化趋势

**判据 2 · 可证伪的条件句** — 必须写成 `如果 A 在 B 之前没做 C，我就 D`，四要素齐全：

> 「如果 v1.0 之前还没把 Windows 路径问题（#4127）解决，我就不在团队里推它了。」
> 「如果下个季度的 release 还是只有 benchmark 没有真实用户案例，我倾向于认为这是刷榜。」

写下条件 = 未来可以被自己打脸 = 真人在跟进。

**判据 3 · 作者赌注** — 一个具体的、有代价的后续动作，且必须是真的：

- 「我给它提了个 issue」（→ 必须有真实 issue 编号；若未真提，改写为「我打算提，草稿写在下面」并真的贴出草稿）
- 「我下个月的 side project 会用它」（→ 登记进 author-log 的承诺队列，下期必须交代）
- 「我给它打了个 patch，diff 在下面」（→ 真实 diff）

**判据 4 · 反向判断** — 明确说某个方向走不通 + 技术理由：

> 「我不觉得它会做 SSR 支持。它的整个渲染模型建立在客户端 DOM 序列化上，`src/core/serialize.ts` 那 200 行没法搬到服务端。要走 SSR 等于重写。」

### §9.2 三条禁令

1. **禁止无主语乐观**：值得期待 / 未来可期 / 相信在不久的将来 / 有望 / 前景广阔 / 让我们拭目以待 / 大有可为 / 星辰大海
2. **禁止抽象趋势句**：生态将进一步完善 / 性能将持续提升 / 社区会越来越大 / 应用场景会更广 / 更多厂商会加入 / 随着…的持续提升和…的成熟
3. **禁止展望作为全文最后一节**（A1/A4/B2/B4 明确规定嵌入前一节末尾；A2/B1 允许成节但后面必须还有结尾节）

### §9.3 两个机械测试

**可移植性测试（portability test）**
把展望段里的产品名/公司名替换成任意同类对象。**若段落依然通顺成立 → 该段是空心段，FAIL，重写。**

> 「X 的未来值得期待，相信在社区的共同努力下会成为该领域的标杆。」→ 换成任何 Y 都成立 → **FAIL**
> 「Page Agent 会让自然语言操控 UI 从尝鲜变成标配，它是推动这个转变的先行者之一。」→ 换成任何 AI 项目都成立 → **FAIL**

**时间无关性测试**
删掉段落里所有日期、版本号、编号。**若段落依然完整成立 → 说明它没有任何真实时间锚 → FAIL。**

### §9.4 篇幅与形式

- 篇幅：Job A ≤200 字且 ≤ 全文 12%；Job B ≤300 字且 ≤ 全文 12%
- 形式由 seed 决定，**不必是独立 H2**，可选：一个 H3 / 一个普通段落 / 3 条 TODO 列表 / 一句嵌在局限节末尾的话 / 一个「接下来要盯的三件事」清单
- 若采用清单形式，每条必须带一个可核对的观察点（「盯 `CHANGELOG.md` 有没有出现 `streaming`」）

### §10.2 标题硬性规则

- 长度 18-38 字（作者真实标题落在此区间）
- **必须含 ≥1 个真实数字或 ≥1 个具体专名**（库名/公司名/API 名）
- 标题里的每个数字**必须在正文有出处且在 manifest 有登记**
- 感叹号 ≤2；emoji ≤1 且只能是 🚨（persona 特征）
- 禁止 §2.1-B/C 的拔高词（革命性/颠覆/里程碑）——但**允许**作者的真实用词（王炸、洗牌、死磕、深度拆解）
- **悬念必须兑现**：禁止疑问句 + 「结果让人意外」类悬念而正文没有对应的反直觉发现（H02）

### §10.3 标题党与正文的落差管理

作者的真实风格是**夸张标题 + 扎实正文**。这个组合恰恰是人类博主的特征；AI 内容农场是**夸张标题 + 空心正文**。因此：

- 标题可以夸张（在模板池范围内）
- **但正文第一节必须在前 100 字内给出硬事实**（代码/数字/报错/编号之一），把标题欠的债立刻还上
- 自检 C25 专门检查这一点

### §10.4 开头 60 字规则

必须以下列之一开场（S09）：一段代码或命令 / 一句报错原文 / 一个精确数字 / 一个 issue 或 commit 标题原文 / 一句不加修饰的断言（「这个库的 dependencies 是空的。」）。

**禁止**：自我介绍、「在阅读本文前」、定义句、时代背景句、无数字的「最近 X 很火」、「本文将…」、「做前端这么多年，我一直在思考…」。

## §12 Rotation 状态机

```
输入: today, job(A|B), rotation-state.json, author-log.md

0. salt 取值
   salt = rotation-state.json.salt[job]        # A/B 各一个固定整数
   salt 必须**稳定**：同一 job 同一 idx 要派生出同一组参数，
   这样一次运行失败后重试不会换骨架（否则证据清单与正文会错位）。
   只有人工想"重新洗牌"时才改 salt，改完记进 author-log。
   若 salt 字段缺失，A 用 3、B 用 11，并立刻补写回文件。

1. seed 计算
   jobA: idx = floor((today - 2026-01-05) / 7)      # 周索引（2026-01-05 是周一）
   jobB: idx = floor((today - 2026-01-01) / 1)      # 日索引
   idx < 0 时取绝对值，不要报错退出。

2. 派生（每项用不同质数乘子，避免相关性）
   variant      = cands[(idx*1  + salt) % len]  + 去重规则
   emojiBudget  = [none, single, sparse, full][(idx*7 + salt) % 4]
   tableMode    = [none, wide, irregular, prose][(idx*11 + salt) % 4]
   h2Count      = [4,5,6,7,8,9][(idx*13 + salt) % 6]  ; ≠ 上一篇
   openingType  = [code, error, number, issueTitle, commitMsg, bluntClaim][(idx*17+salt)%6]
   endingType   = [decision, openQuestion, todoList, oneLineVerdict, nextWeekHook][(idx*19+salt)%5]
   targetWords  = [1800,2200,2600,3000][(idx*23+salt)%4] ; |Δ 上一篇| ≥300
   titleTpl     = T[(idx*29+salt)%8] ; 不在最近 4 篇中
   outlookForm  = [h3, inline-paragraph, todo-list, embedded-in-limits][(idx*31+salt)%4]
   styleBlock   = ((idx*37+salt) % 100) < 35
   highlightBox = ((idx*41+salt) % 100) < 40

3. 去重校正：任一项与 rotation-state 最近 N 条冲突 → idx+1 重算该项

4. 特例覆盖：材料不足 → 强制 A5/B4；clone 失败 → A4；抓取失败率 >30% → abort

5. 运行结束（无论成败）：写回 rotation-state.json + author-log.md + evidence
```

**为什么必须外置状态**：无状态的 cron 每次都会收敛到「最可能的输出」，也就是最像 AI 的那个输出。外置状态 + 去重校正，是把「随机性」变成「可核对的历史」，既保证多样性，又保证跨篇一致性（原则一）。

## §13 交付物清单与资源管线

### §13.1 每次运行产出

| 文件 | 条件 | 入库 |
|---|---|---|
| `_posts/YYYY-MM-DD-{slug}.md` | **仅在 32 项自检全 PASS 且构建成功后写入** | ✅ |
| `assets/img/{slug}/banner.webp` + `NN-*.webp` + `prompts/` | 随文章产出 | ✅ |
| `_drafts/evidence/{slug}.md` | **无条件写入**（含 abort 情况） | ❌ gitignore |
| `_drafts/author-log.md` | 追加一段（含结论、承诺、悬置疑问、rotation 参数） | ✅ |
| `_drafts/rotation-state.json` | 更新 | ✅ |
| 运行日志中的 `[SELF-AUDIT]` 报告全文 | 无条件输出 | — |

### §13.2 博客文章格式约定（不可违反）

文件名：`_posts/{YYYY-MM-DD}-{小写英文kebab-slug}.md`

frontmatter **只用这 7 个键、按此顺序**：

```yaml
---
layout: post
title: <18-38 字，符合 §10>
subtitle: <真正的一句话导语，不要复制 title>
date: YYYY-MM-DD          # 必须与文件名日期完全一致
categories: <空格分隔，单 token>
cover: /assets/img/<slug>/banner.webp
tags: <空格分隔，每个必须单 token>
---
```

- **`tags` / `categories` 是空格分隔字符串，不是 YAML 列表。** `Vibe Coding` 会被 Jekyll 拆成 `Vibe` + `Coding` 两个 tag（`_posts/2026-07-12-impeccable-ai-design.md` 已中招，`tags.html` 里能看到碎片）。多词概念用中文复合词或连字符。
- 禁止未来日期（`_config.yml` 无 `future: true`，Jekyll 会静默丢弃文章）。
- 禁止使用 7 键之外的字段（`permalink` / `description` / `license` / `updated` / `draft` 等**全站无人读取**，加了也没用）。
- 正文第一行 `# {title}`，第二行封面图 `![{中文描述性alt}](/assets/img/{slug}/banner.webp)`。
- 图片**一律绝对路径** `/assets/img/...`，禁止相对路径，禁止手写 `/better-blog` 前缀（`_plugins/add_baseurl_filter.rb` 会自动注入 baseurl）。
- slug 全小写且不与既有文章重复（Linux 大小写敏感，GitHub Pages 跑在 Linux 上）。
- 结尾可写 `项目地址：[https://github.com/xxx](https://github.com/xxx)`（既有约定）。
- **不要改已发布文章的 slug 或 date**——Waline 的评论与阅读量以 `page.url` 为键，改了会孤立历史数据。

### §13.3 图片管线（本机实测过的命令，勿凭记忆改）

```bash
# 1. 生成（两个 skill 都必须先写 prompts/ 再出图，这是 skill 的硬性要求）
#    封面：baoyu-cover-image --quick --aspect 16:9 --text none
#    插图：baoyu-article-illustrator，直接生成不用确认，
#          type 按内容选，style=sketch-notes，density=balanced(3-5张)，语言 zh
#    后端走运行时原生出图工具（本机无 DASHSCOPE_API_KEY，不要尝试 dashscope provider）
#
#    ⚠️ 原生出图工具把 PNG 写到**仓库根的 `vibe_images/`**，文件名形如
#       `{name}_{毫秒时间戳}_{8位hash}.png`，不是写进文章目录。搬运时按此路径找。
#       该目录已加入 .gitignore 与 _config.yml exclude，但**仍要在收尾时删掉本次产生的文件**，
#       否则每跑一次就堆一批 ~2MB 的 PNG。

# 2. 搬运到博客约定位置
mkdir -p assets/img/{slug}
#    封面           → assets/img/{slug}/banner.png
#    插图           → assets/img/{slug}/NN-{type}-{name}.png
#    prompts/ 整体  → assets/img/{slug}/prompts/
#    （仓库已有先例：assets/img/page-agent/prompts/01-scene-banner.md）

# 3. 转 webp —— 用 ffmpeg，不要用 cwebp
#    ❌ /usr/local/bin/cwebp 1.5.0 编译时没带 libpng，读不了 PNG，
#       任何 PNG 都报 "PNG support not compiled"，管线会在这里整体断掉。
#    ❌ macOS 自带 sips 能读 webp 但不能写（Unsupported output format）。
#    ✅ ffmpeg 的 libwebp 可用，产物是 VP8 lossy，与既有资源编码一致。
#       scale 用 min(1600,iw) 对齐既有资源的 1600px 宽，同时避免把方形插图无意义上采样。
for f in assets/img/{slug}/*.png; do
  ffmpeg -hide_banner -loglevel error -y -i "$f" \
         -vf "scale='min(1600,iw)':-2" -c:v libwebp -quality 82 \
         "${f%.png}.webp" && rm "$f"
done
#    实测：1792x1024 PNG 1.99MB → 1600x914 WebP 42KB，
#    与 assets/img/page-agent/banner.webp（1600x914 VP8 lossy）格式完全一致。

# 4. 把正文与 frontmatter cover 里的 .png 引用改成 .webp

# 5. 清理本次的原生出图中间产物
rm -f vibe_images/*.png
```

**文件名必须全 ASCII**——commit `8dd87af` `fix(assets): 重命名中文命名静态文件为 ASCII 名，修复 Jekyll 构建崩溃`。
