# 一份 24 页的扫描件，它吐给我 8192 个字符

![一份扫描件被喂进模型上下文的过程](/assets/img/pdf2txt-fixture/cover.webp)

> 一句话结论：这类工具的价值不在解析精度，在它先把多少页换算成了多少 token，选型该先看这一步。
> 现在该做什么：别拿官方样例试，拿你自己最脏的那份扫描件跑一次，量它吐进上下文的字符数再决定。

## 我手上那份 24 页的扫描件，直接贴进对话要两万六千多字符

差别在输出对象。老牌 PDF 转文本工具给人读，排版得留；它给模型读，层级不能丢，排版可以丢。

我原来用的是另一家，它的默认输出给人看，缩进和表格线都留着，喂进对话之前我还得自己再洗一遍。

我关注它是上周：[mmorett/pdf2txt](https://github.com/mmorett/pdf2txt) 的 star 数 18742，
27 日下午抓的，比上期快照高一档。

同一份文件我贴进对话要两万六千多字符，模型读到第 6 页就开始漏表格，翻回第 2 页它已经不认得了。

![第一次跑完的终端输出，末尾那行字符数就是 8192](/assets/img/pdf2txt-fixture/01-screenshot-first-run.webp)

## 装完直接指一个 pdf，0.9 秒出结果

```bash
pnpm add -D pdf2txt
npx pdf2txt scan.pdf --tokens 4000
```

跑完 stdout 是 8192 个字符，24 页每页前面还多一行页码。

那 24 行是噪声，得加 --no-pagenum 才是能直接喂的形态。这个我没在 README 里看到，
是把它输出丢进 wc -l 才发现的：41 行里 24 行是 `[p 3]` 这种前缀。

## 8192 不是它压出来的，是页数先被折成预算

它没有做压缩。`--tokens 4000` 是分配额度：24 页分完，每页剩多少就截在哪。
同一份文件把额度调高一档，出来的不是同一份的长短两版，是后 3 页能不能进来的区别。

这条我为什么盯得这么紧：日报流程里我一天喂它 6 份合同，字符数直接乘以 6 就是当月的账单。
分配写在 CLI 参数里，而不是藏在它自己的默认值里，是它跟同类拉开的地方——默认值我改不了，参数我能改。

[mmorett/pdf2txt](https://github.com/mmorett/pdf2txt) 的 README 只写了「为 LLM 优化」。
优化的是分配，不是精度。同类里 prompt 最长的那家 2614 字符，它只占 412。

| 维度 | 它 | 老牌那家 |
| --- | --- | --- |
| 一次调用占的上下文 | 412 | 2614 |
| 表格还原 | 能对上 | 拆散 |
| 多文件 | 不支持 | 支持 |

## 退码 137 的那次 300 页合并件，412 字符的便宜我没占到

同一个命令，我换了输入。300 页的合并件，它先把整份读进内存再算分配，
进程被内核干掉，zsh 报 killed，退码 137。412 字符的便宜，到这一步变成了 0。

![它把双栏合同的左右顺序读串的那一步](/assets/img/pdf2txt-fixture/02-diagram-two-column-flow.webp)

版式全丢是同一批代价。双栏合同的右栏接在左栏之后，第 3 条读起来像在说第 7 条的事，
我读第二遍才发现这个串行。

我会留它，但不进 CI。还在 0.x，issue 里 --pages 那个参数
[mmorett/pdf2txt#318](https://github.com/mmorett/pdf2txt/issues/318) 挂了两个月没定稿。
同类那家支持多文件，可它的 prompt 本身就比它的输出长，喂两份进去，光说明书占掉的比我读的东西多。

## 如果 --pages 在 v1.0 前定稿，我就把它换进日报流程

条件很具体。到 11 月底 --pages 还没定稿、多文件那条 TODO 还是注释，
我就自己写个 60 行的包装，分页交给上游的 pdftk，这事到此为止。

300 页那次只跑了一遍，剩下的我没测：换台机器、换个 node 版本是什么读数，我没验到。
